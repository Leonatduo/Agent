1	Agent 和普通 LLM 的本质区别是什么？	Agent面试第一问，必考
LLM是大语言模型， 基于海量数据训练， 可以根据用户提问去思考然后生成用户想要的回答， 但是不具备自主决策，记忆管理相关功能， 相当于大脑的角色， Agent则是以LLM为核心的框架， 在LLM基础上增加了记忆管理， 自主规划， 工具调用等模块，可以根据用户问题自主分析决策是否调用工具以及调用什么工具回答用户问题， 并根据生成的回复进一步引导进一步提问和回答， 同时根据用户提问生成对用户的画像方便后续定制化回复。 

2	ReAct 是什么？和 CoT 有什么区别？	Agent最核心的框架概念
CoT（思维链）是一种提示词工程技巧。它的核心是让模型面对复杂推理题（比如数学逻辑）时，把隐式的推理步骤显式地写出来，即‘一步一步想’，从而减少直接跳步导致的幻觉。但它只依赖模型内部的静态知识。

而ReAct是一种Agent的决策范式，全称是 Reasoning + Acting。它的运行机制是一个紧耦合的循环：模型先思考（Thought）该怎么做，然后执行一个行动（Act）（比如调API），紧接着环境会返回一个观察结果（Observation），模型再根据这个Observation去修正下一步的Thought，直到任务完成。

两者最本质的区别在于： CoT是‘纸上谈兵’，只推理不行动，错了也无法修正；而ReAct是‘实践出真知’，通过与环境交互获取实时反馈，实现了动态纠错。因此在需要调用工具或获取实时信息的Agent场景中，ReAct是标配。”

3	Plan-and-Solve 和 ReAct 的优劣对比
Plan-and-Solve 说白了就是‘先想好再做，一口气干完’。它拿到问题后，先自己规划出完整的解决步骤，然后按步骤一次性把答案算出来，中间不再回头。所以它特别适合那种路径清晰、不太需要外部信息的任务，比如解数学题、逻辑推理。好处是快、省token，坏处是一旦规划错了，那就全错了。

ReAct 刚好相反，它是‘边想边干，干完再看，看完再想’的循环。准确流程是：先思考（Thought）我要干嘛，然后行动（Action）去查工具或算一步，再看观察结果（Observation），根据这个结果再决定下一步怎么想、怎么动，直到最后给出最终答案。它不是‘回答完了再反思’，而是每一步都在循环里动态调整。


4	Tool Calling 和 ReAct 的关系
“Tool Calling 是模型的一种底层能力，就是让模型能输出结构化的工具调用指令，系统去执行函数然后把结果喂回来。

ReAct 是上层的行动策略，它的核心是多轮‘想→做→看→再想’的循环。在这个循环里，当它决定要‘做（Action）’的时候，通常会借助 Tool Calling 来实现工具调用。

5	多 Agent 协作 vs 单 Agent 多工具
单 Agent 多工具，是一个 Agent 大脑持有全部工具，依靠 ReAct 循环完成任务，实现简单，信息天然共享，延迟低。但工具一多、上下文太长，会出现工具选错、信息遗忘幻觉的问题，适合步骤不多、工具数量有限的任务。

多 Agent 协作是把任务拆分成多个具备独立角色的 Agent，每个 Agent 拥有自己的 prompt、工具集，通过编排器调度分工。优势是职责解耦，每个 Agent 专精自己的领域，可以规避长上下文问题，方便业务扩展；但代价是架构变复杂，需要处理任务调度、Agent 间信息同步，延迟也会增加。

选型上我遵循一个原则：优先单 Agent 多工具做 MVP，当出现工具爆炸、上下文超限、业务模块需要独立迭代的时候，再引入多 Agent，避免过度设计。同时工程上更多用**编排式多 Agent，而不是自由对话式多 Agent**，可控性更强，适合生产环境。


7	LangGraph 的 State 和 Reducer 机制
State是LangGraph中在节点间传递的数据共享容器， Reducer是指在State字段上的合并策略， 一般来说多节点在对Graph中的某个字段做修改的时候都是粗暴的新值替换旧值， 但是Reducer机制可以
根据一定策略比如取最大值， 并集的方式替换旧值，其中最经典的是message字段， 通过Reducer采用add_message的方式追加到message中。

13	上下文窗口溢出怎么解决？
上下文窗口溢出主要针对两种情景
一种是输入层面的上下文窗口溢出， 针对这种情况主要可以通过
1.滑动窗口， 只保留最近k条信息，前面的对话舍弃
2.把过去的对话轮次信息总结成一个摘要
3.通过RAG， 把历史对话存起来，每次只捞和当前问题相关的几个对话

第二种是在LangGraph这种框架中， state中存储的内容太多导致溢出， 这个时候可以利用Reducer机制限制只保存最近的几次信息，
或者说用check_pointer机制把消息持久化到db里

17	多路向量检索如何加权合并？
> 多路检索最大的问题是不同检索通路输出的分数量纲和分布不一致，**不能直接原始分数相加**。工业界主要有两种合并方案。

第一种是归一化后分数加权融合：先对每一路召回结果内部做分数归一化映射到 0‑1 区间，再给每一路设置权重做加权求和，最后按总分排序。优点是可以直接控制分数贡献；但缺点很明显，归一化容易被异常分数干扰，固定权重很难适配所有查询，调参成本高。

第二种是 RRF 倒数排名融合，也是生产环境首选。它**不依赖原始相似度分数，只依靠文档在每一路的排名位次**，公式是对每一路的 1/(k+rank) 累加求和，k 一般取 60。也可以扩展成加权 RRF，给不同检索通道配置权重。它规避了分数归一化的麻烦，稳定性好，多路都靠前的文档会获得更高分数。缺点是丢失原始分数信息。
