 q1.为什么要分库，
 具体问题存在具体库里， 方便后续维护， 然后的话也方便并行查库时的检索效率，避免堆在一起， 同时召回文档的时候也可以避免无关文档的干扰

这里假定用户问的问题在agent的引导下已经足够具体，可以具体到一些前提条件（国家, 产品, 主体条件）然后后面就知道去哪各库里去检索了
 q2.“检索自省”是什么意思？怎么判断一篇文档“足以”回答子问题？
 这里的自省主要是对生成文档的完备性校验， 以及判断当前子问题召回的文档是否足够回答用户的合规问题，  而不是单纯的靠RAG的召回文档打分（这里RAG采用检索策略是按照稀疏索引和稠密索引的混合检索， 召回后用RRF算法取Top5）, 然后召回后会有一层自省过程来
 结合子问题和这top5文档判断当前文档信息是否足够回答子问题, 返回结构化结果。

Q6：你说“信息严重不足自动转人工”，那“严重不足”怎么量化？阈值设多少？为什么设这个数？
这里信息严重不足指的子问题召回文档信息是否足以回答子问题的评估， 假如用户问题很简单但是召回文档不够回答那就是严重不足， 但是如果用户问题可以拆几个子问题， 这里一般最多三个， 不然的话就前置引导用户问具体一些， 三个子问题如果有两个子问题能答但是一个不能答，
那就可以回答问题生成报告，只是那一个子问题回答不了， 引导业务人员去人工带着回答的两个子问题去回答

Q7：多库并行检索的“并行”是真正的并行吗？在技术实现上怎么做到？
回答要点：

在 LangGraph 中用 Send API 或 asyncio.gather() 实现真正的并行异步调用，N 个库同时发起检索请求，等待所有返回后再聚合。

不是串行排队，耗时 = 最慢的那个单库查询时间，而不是 N 倍时间。

还可以展开：每个子问题的多个库检索也是并行的，整体形成一个 “扇出-扇入”模式。

Q8：自省校验怎么做的？是用另一个LLM来评估检索结果，还是用规则？
回答要点：

分层设计：第一层用规则做快速拦截（相似度阈值、文档数量、是否包含关键实体）；第二层用小参数LLM做语义级评估（比如用较便宜的模型判断“这篇文档是否正面回答了该子问题”）。

为什么不直接用大模型自省？成本和延迟。每个子问题都让大模型自省会成倍增加Token消耗，所以用规则+小模型组合，只在必要时才上大模型。

也可以提：自省结果会反哺检索策略——如果发现某个库总是召回无效文档，动态降低该库的权重。

Q9：“降低幻觉风险”这个效果，你怎么量化证明的？（面试官可能看你简历里写了“从12%降至3%以下”）
回答要点：

定义“不可信片段”：人工抽检时判定为“无任何检索原文支撑”的句子。

对比实验：关闭自省+事实核查链路时，测试集上不可信片段占比约12%；开启后降至3%。

人工抽检方式：合规专家双盲标注（标注者不知道是机器还是人工写的），每轮抽样XX条问答，统计“完全支撑/部分支撑/无支撑”比例。

Q10：如果自省判断“资料不足”，但用户坚持要求回答（比如投诉为什么这么简单的问题都答不上来），你怎么处理？
回答要点：

产品策略层面：不妥协，合规是红线，用户体验不能凌驾于合规之上。

交互层面：提供替代路径——“虽然无法给出确定答案，但您可以参考以下相关条款（附上已召回的文档链接），或点击此处发起人工咨询。”

系统层面：记录该次“用户拒绝转人工”的行为，存入State供后续审计；如果同一用户频繁触发资料不足，可提升其咨询优先级，主动触发人工回访。

Q11：这个系统设计里，你认为最大的风险点在哪里？如果让你改进，你会改什么？
回答要点：

诚实回答（体现思考深度）：最大风险在于自省模块本身的判断准确率——如果自省误判“资料充足”而实际不够，幻觉就会漏出去。

改进方向：①增加人工抽检反馈闭环，业务人员打标“答案不可信”的Case自动回流作为测试用例，定期调优自省阈值；②引入置信度校准，让自省模块输出概率而非二值，低置信度时强制走人工。
